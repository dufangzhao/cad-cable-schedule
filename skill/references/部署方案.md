# 部署方案：把选中汇总做成不依赖 agent 的服务

面向"其他同事自己用"的场景。核心结论：本 skill 的汇总逻辑是**纯 Python 文件处理**，
唯一与 CAD/agent 耦合的环节是"怎么拿到电缆表文字"。把这一环换成文件导出，就能脱离 agent 独立部署。

## 分层：内核 / 外壳

```text
内核（唯一口径来源，必须复用，不得各写一份）
  scripts/电缆汇总统计.py   表识别 + 行聚类 + 型号/芯数/截面三项汇总 + Excel 生成
    ├─ 输入：read_drawing_structure artifact（scope=selected）   ← agent 路径
    └─ 输入：DXF                                                  ← 服务/单机路径

外壳（任选，互不冲突）
  A. agent + skill          当前形态，人工触发，能力最全
  B. 命令行 / 单机可执行      工程师本机拖拽即用，零网络
  C. 内网网页服务            浏览器上传 DXF → 下载 Excel
  D. AutoCAD 插件            选中后一键，结果直接弹回 CAD
  E. 共享文件夹监听          投递即出结果，适合不碰 CAD 的采购/设计
  F. 内网 MCP 服务           多台机器共用一个 CAD 读图与汇总能力
  G. 公网智能体平台          仅限非敏感图纸，或改为"只传汇总 JSON"
```

**关键实测结论**：整图 DXF（11.4 MB、9045 个实体、无任何选择集）与选择集得到**完全一致**的结果
（7 张表 / 170 行 / 49 类 / 145 根），耗时约 4 秒。因此网页方案**不需要用户在 CAD 里先选中**，
也不需要服务器上有 AutoCAD 或 MCP——只要拿到 DXF 就行。这是所有轻量方案成立的前提。

## 取数方式（决定用户体验）

| 方式 | 操作 | 是否需要插件 | 适用 |
|---|---|---|---|
| 整图另存 DXF | `SAVEAS` → DXF（AutoCAD 2018 格式） | 否 | 首选，最省事，自动覆盖全图所有电缆表 |
| 选中导出 | 选中电缆表 → `WBLOCK` 写成 DXF | 否 | 只想要某几张表，文件小、上传快 |
| 插件直传 | 选中 → 按钮 → HTTP POST | 是 | 体验最好，能精确复刻"选中"语义 |

DXF 必须是文字可读的 ASCII/UTF-8 编码导出，且三维/代理实体不影响识别（只读 TEXT/ATTRIB）。

## 方案 C：内网网页服务（推荐先做）

网页服务与 CAD 插件是**独立交付物**，各自打包、各自分发（互不依赖，可单独给不同的人）：

| 交付物 | 使用者 | 依赖 | 内容 |
|---|---|---|---|
| `cable-summary-offline-plugin` | CAD 设计师 | 只要 AutoCAD | LISP 插件 + 单文件 exe + 一键脚本，**不联网、不装 Python、不需服务** |
| `cable-summary-web-service` | 不会 CAD 的同事 | 服务端 Python | FastAPI 服务 + 前端页 + 一键脚本 |
| `cad-cable-schedule`（本 skill） | 用 agent 的人 | DSH/agent | 端子解析、出图、选中汇总 |

三者共用同一份汇总内核（型号+芯数+截面三项一致即合并），内核权威实现是本 skill 的
`scripts/电缆汇总统计.py`；改口径后必须同步到另外两个交付物，否则数量会分叉。

- `GET /`：上传页（浏览器直出，无需前端构建）
- `POST /api/summarize`：接 DXF，返回汇总统计与 `待确认` 项
- `GET /api/download?id=<ticket>`：一次性取件下载 Excel

实测：11.4 MB DXF 全流程约 4.8 秒；DWG、伪装 DXF、空文件分别返回 415/415/422。

生产化还需要补齐（原型未做）：

- **并发**：DXF 解析是 CPU 密集且约 4 秒/张，用 `--workers` 开多进程或用任务队列；
  同一份图纸多人重复上传可用文件哈希做结果缓存。
- **限制**：上传大小上限（原型 64 MB）、按用户/IP 限流、请求超时。
- **占位**：临时目录必须请求结束即清理（原型用 `mkdtemp` + 一次性 ticket）；
  正式环境建议加定时清扫，避免磁盘被临时文件吃满。
- **部署**：nginx 反向代理时注意 `client_max_body_size` 要大于图纸体积；
  Windows 服务器可用 `nssm` 注册成服务，Linux 用 systemd。
- **安全**：内网可加企业 SSO 或反向代理白名单；不要暴露到公网——图纸是商业资产。

## 方案 D：AutoCAD 插件（体验最好）

AutoLISP 约 50 行即可：取 `ssget "I"`（当前选择集），遍历 `TEXT/ATTRIB` 收集
插入点、字高、文字、图层，序列化成 JSON，经 `vl-file-decode`/`MSXML2.XMLHTTP`
POST 给服务，再用 Shell 打开下载的 Excel。好处是复刻"选中"语义、工程师不用离开 CAD；
代价是要分发插件、做版本兼容（AutoCAD 2020 与 2024 的 .NET API 有差异，纯 LISP 更省心）。

## 方案 E：共享文件夹监听

服务只监视一个网络共享目录：投递 `*.dxf` → 自动生成同名 `*_电缆汇总表.xlsx`。
不改任何客户端，采购/设计把文件拷进去就行。适合"发文—汇总"这种批处理场景，
但要注意目录权限和重名覆盖策略。

## 方案 F：内网 MCP 服务

把"读 CAD + 汇总"做成团队共用的 MCP 端点：一台装了 AutoCAD 的机器常驻 MCP，
其他同事的 agent（含 DSH、Claude、Cursor 等）通过 SSE/HTTP 连过来。
此时 `cad-cable-schedule` 的 Survey 模式**一行不用改**，因为 `read_drawing_structure`
的 `scope="selected"` 语义在服务端依然成立。风险是那台机器的 CAD 会话被多人共享，
需要排队与超时保护；另外 MultiCAD 的 `read_drawing_structure` 目前读的是**当前活动文档**，
多人并发时"活动文档"会互相踩，必须做会话隔离或串行化。

## 方案 G：公网智能体平台

可行但要想清楚数据边界：智能体平台大多需要把图纸上传到第三方。
- 敏感图纸不要走公网；确有需要时只上传**已知不含敏感信息的电缆表片段**（WBLOCK 导出）。
- 更稳妥的折中：把 `cable-summary.json` 作为交接格式，平台上只做"汇总 JSON → Excel"，
  图纸始终留在内网。内核的 `extract` 已经同时输出该 JSON。
- 平台侧只需要 Python 运行时 + openpyxl，无 CAD 依赖。

## DWG 直接上传（可选增强）

若不想让用户手动另存 DXF，可在服务器侧接 **ODA File Converter**（官方免费下载，
提供命令行接口，支持 Linux/Windows）。注意其协议对"免费版用于商业/生产服务"的许可
边界需要与法务确认，替代方案是保留一台 Windows 机器用 CAD 做 DWG→DXF 批量转换。

## 落地顺序建议

1. **方案 B/C 并行最快见效**：网页服务交付物已就绪，先在内网一台机器跑通，
   选 2~3 个同事试用，确认口径无异议。
2. 口径稳定后再做**方案 D 插件**提升体验，或 **E 文件夹监听**覆盖非 CAD 用户。
3. 有多个团队要复用时再上 **F**，把内核与 CAD 能力都服务化。

无论哪种外壳，都必须复用 `scripts/电缆汇总统计.py`，不得各写一份汇总逻辑——
否则"型号+芯数+截面三项一致即合并"的口径会分叉，采购数量对不上。
